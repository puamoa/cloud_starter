# CI/CD 파이프라인 이론

Step 8-2와 8-3에서 GitHub Actions를 사용하여 프론트엔드/백엔드 배포를 자동화합니다.  
이 세션에서는 그 배경이 되는 CI/CD 이론을 학습합니다.

---

## 1. CI/CD란?

### 주요 용어

| 용어                                    | 설명                                                     |
| --------------------------------------- | -------------------------------------------------------- |
| **CI (Continuous Integration)**         | 코드 변경을 자주 통합하고 자동으로 빌드·테스트하는 관행  |
| **CD (Continuous Delivery/Deployment)** | 검증된 코드를 자동으로 스테이징/프로덕션에 배포하는 관행 |
| **파이프라인 (Pipeline)**               | 빌드 → 테스트 → 배포를 자동화한 일련의 단계              |
| **아티팩트 (Artifact)**                 | 빌드 결과물 (JAR, Docker Image, 번들 파일 등)            |

> [!CONCEPT] CI/CD 핵심 개념
> CI(Continuous Integration)는 개발자가 코드를 자주 통합하고 자동으로 빌드·테스트하는 관행이고, CD(Continuous Delivery/Deployment)는 검증된 코드를 자동으로 스테이징/프로덕션에 배포하는 관행입니다.  
> 수동 작업을 자동화하여 배포 속도와 품질을 동시에 높입니다.

### CI/CD 파이프라인 전체 흐름

```
┌──────────────────────────────────────────────────────────────────────┐
│                         CI/CD 파이프라인                             │
│                                                                      │
│  ┌───────┐   ┌───────┐   ┌────────┐   ┌─────────┐   ┌────────────┐   │
│  │ 코드  │──►│ 빌드  │──►│ 테스트 │──►│ 스테이징│──►│ 프로덕션   │   │
│  │ Push  │   │ Build │   │ Test   │   │ Stage   │   │ Production │   │
│  └───────┘   └───────┘   └────────┘   └─────────┘   └────────────┘   │
│                                                                      │
│  ├────── CI (지속적 통합) ──────────┤├──── CD (지속적 배포) ──────┤  │
│                                                                      │
│  자동화: 코드 변경 → 빌드 → 테스트 → 배포 (수 분 내 완료)            │
└──────────────────────────────────────────────────────────────────────┘
```

### CI/CD 도입 전후 비교

| 항목            | CI/CD 없이       | CI/CD 적용        |
| --------------- | ---------------- | ----------------- |
| **배포 빈도**   | 월 1~2회         | 일 수회~수십 회   |
| **배포 시간**   | 수 시간          | 수 분             |
| **실패율**      | 높음 (수동 실수) | 낮음 (자동 검증)  |
| **복구 시간**   | 수 시간          | 수 분 (자동 롤백) |
| **개발자 경험** | 배포 스트레스    | 코드에 집중       |

## 2. 빌드 / 테스트 / 배포 단계

> [!CONCEPT] 파이프라인의 3단계
> CI/CD 파이프라인은 **빌드**(Build), **테스트**(Test), **배포**(Deploy) 세 핵심 단계로 구성됩니다.  
> 각 단계는 이전 단계가 성공해야 다음으로 진행되며, 실패 시 즉시 개발자에게 알림을 보냅니다.

### 각 단계의 역할

```
┌─────────────────────────────────────────────────────────┐
│  1. 빌드 (Build)                                        │
│  - 소스 코드 컴파일                                     │
│  - 의존성 다운로드 (npm install, gradle build)          │
│  - 정적 분석 (lint, code style)                         │
│  - 아티팩트 생성 (JAR, Docker Image)                    │
├─────────────────────────────────────────────────────────┤
│  2. 테스트 (Test)                                       │
│  - 단위 테스트 (Unit Test)                              │
│  - 통합 테스트 (Integration Test)                       │
│  - E2E 테스트 (End-to-End)                              │
│  - 보안 스캔 (SAST, 의존성 취약점)                      │
├─────────────────────────────────────────────────────────┤
│  3. 배포 (Deploy)                                       │
│  - 스테이징 환경 배포                                   │
│  - 스모크 테스트 (기본 동작 확인)                       │
│  - 승인 (수동 또는 자동)                                │
│  - 프로덕션 배포                                        │
└─────────────────────────────────────────────────────────┘
```

### 테스트 피라미드

```
                    ┌───────┐
                    │  E2E  │  느림, 비용 높음, 적게
                    │ Tests │
                 ┌──┴───────┴──┐
                 │ Integration │  중간
                 │    Tests    │
              ┌──┴─────────────┴──┐
              │    Unit Tests     │  빠름, 비용 낮음, 많이
              └───────────────────┘

권장 비율: Unit 70% / Integration 20% / E2E 10%
```

## 3. 배포 전략

> [!CONCEPT] 배포 전략 비교
> 배포 전략은 새 버전을 프로덕션에 릴리스하는 방법을 정의합니다.  
> 각 전략은 다운타임, 위험도, 롤백 속도에서 트레이드오프가 있으며, 서비스 특성에 맞게 선택해야 합니다.

### Rolling 배포

```
시간 →
서버1: [v1][v1][v2][v2][v2][v2]  ← 먼저 업데이트
서버2: [v1][v1][v1][v2][v2][v2]  ← 다음 업데이트
서버3: [v1][v1][v1][v1][v2][v2]  ← 마지막 업데이트

특징: 순차적으로 하나씩 교체
장점: 리소스 추가 불필요
단점: 배포 중 v1/v2 혼재 (호환성 필요)
```

### Blue-Green 배포

```
배포 전:                         배포 후 (트래픽 전환):
┌───────────┐                    ┌───────────┐
│  Blue     │ ◄─ LB              │  Blue     │  ← 롤백용 유지
│  (v1)     │                    │  (v1)     │
└───────────┘                    └───────────┘
┌───────────┐                    ┌───────────┐
│  Green    │  ← 대기            │  Green    │ ◄─ LB
│  (v2)     │                    │  (v2)     │
└───────────┘                    └───────────┘

특징: 두 환경을 동시에 유지, LB로 즉시 전환
장점: 다운타임 제로, 즉시 롤백 가능
단점: 2배 리소스 비용
```

### Canary 배포

```
단계 1: 5% 트래픽을 v2로
┌────────────┐  95%  ┌──────────┐
│  v1 (기존) │ ◄──── │    LB    │
└────────────┘       │          │
┌────────────┐   5%  │          │
│  v2 (신규) │ ◄──── │          │
└────────────┘       └──────────┘

단계 2: 문제 없으면 25% → 50% → 100%

특징: 소수 사용자에게 먼저 배포 후 점진적 확대
장점: 위험 최소화, 실제 트래픽으로 검증
단점: 복잡한 라우팅 설정 필요
```

### 배포 전략 비교표

| 전략           | 다운타임 | 롤백 속도 | 리소스 비용 | 복잡도 | 위험도 |
| -------------- | :------: | :-------: | :---------: | :----: | :----: |
| **Rolling**    |   없음   |   느림    |    동일     |  낮음  |  중간  |
| **Blue-Green** |   없음   |   즉시    |     2배     |  중간  |  낮음  |
| **Canary**     |   없음   |   빠름    |    +소량    |  높음  |  최저  |
| **Recreate**   |   있음   |   느림    |    동일     |  최저  |  높음  |

> [!TIP]
> Step 8에서 사용하는 배포 방식은 **Recreate**(재시작) 또는 **Rolling** 수준입니다.  
> EC2 1대에 SSM으로 재시작하는 방식은 Recreate에 가깝고, Auto Scaling Group에서 인스턴스를 순차 교체하면 Rolling입니다.

## 4. Git 브랜치 전략

> [!CONCEPT] Git 브랜치 전략
> **브랜치 전략**은 팀이 Git 브랜치를 어떻게 사용할지 정의하는 규칙입니다.  
> 프로젝트 규모와 배포 빈도에 따라 적합한 전략이 다릅니다.

### GitHub Flow (이 실습에서 사용)

```
main     ──●──●──●──●──●──●──  (항상 배포 가능)
           │  │  │  │  │  │
feature/A ─┘  │  │  │  │  │    (PR → Review → Merge → 자동 배포)
feature/B ────┘  │  │  │  │
bugfix/C  ───────┘  │  │  │
feature/D ──────────┘  │  │
feature/E ─────────────┘  │

규칙: main은 항상 배포 가능 상태 유지
적합: CI/CD가 잘 갖춰진 팀, 빈번한 배포
```

### Git Flow (대규모 프로젝트)

```
main     ─────●─────────────────●─────  (릴리스만)
              │                 │
release  ─────┼──●──●──────────●┤        (릴리스 준비)
              │  │             ││
develop  ──●──●──●──●──●──●──●─●●──●──  (개발 통합)
           │     │     │     │
feature/A ─┘     │     │     │
feature/B ───────┘     │     │
hotfix    ───────────────────┘          (긴급 수정)

적합: 릴리스 주기가 긴 프로젝트 (월 1~2회)
```

### 비교

| 항목          | Git Flow            | GitHub Flow    |
| ------------- | ------------------- | -------------- |
| **브랜치 수** | 많음 (5종류)        | 적음 (2종류)   |
| **복잡도**    | 높음                | 낮음           |
| **배포 빈도** | 낮음 (계획적)       | 높음 (수시)    |
| **적합 팀**   | 대규모, 릴리스 관리 | 소규모, 애자일 |

## 5. 모노레포 vs 멀티레포

> [!CONCEPT] 리포지토리 전략
> 프론트엔드와 백엔드를 하나의 레포에 관리할지(모노레포), 분리할지(멀티레포)는 팀 구성과 배포 주기에 따라 결정합니다.

### 모노레포 (Monorepo)

```
my-project/
├── frontend/          ← Vue.js
├── backend/           ← Spring Boot
├── infra/             ← CloudFormation
└── .github/workflows/
    ├── deploy-frontend.yml  (paths: frontend/**)
    └── deploy-backend.yml   (paths: backend/**)
```

### 멀티레포 (Multi-repo)

```
my-frontend/           ← Vue.js 전용 레포
├── src/
├── .github/workflows/deploy.yml
└── package.json

my-backend/            ← Spring 전용 레포
├── src/
├── .github/workflows/deploy.yml
└── build.gradle
```

### 비교

| 항목          | 모노레포               | 멀티레포                |
| ------------- | ---------------------- | ----------------------- |
| **동시 변경** | 하나의 PR로 관리       | 각각 PR 필요            |
| **CI/CD**     | `paths` 필터로 분기    | 레포 = 배포 단위 (단순) |
| **팀 권한**   | 레포 레벨 분리 불가    | 레포별 독립 권한        |
| **공유 코드** | 쉬움 (같은 레포)       | 별도 패키지 배포 필요   |
| **적합**      | 소규모 팀, 풀스택 개발 | 프론트/백엔드 팀 분리   |

> [!NOTE]
> 이 실습에서는 **멀티레포** 방식을 사용합니다.  
> 프론트엔드 레포와 백엔드 레포를 각각 만들고, 각 레포에 독립된 배포 워크플로우를 작성합니다.

## 6. 환경 분리 (dev/staging/prod)

> [!CONCEPT] 환경 분리의 필요성
> **환경 분리**는 개발(dev), 스테이징(staging), 프로덕션(prod) 환경을 독립적으로 운영하여 코드 변경이 사용자에게 영향을 주기 전에 충분히 검증하는 전략입니다.

### 환경별 역할

| 환경            | 목적                        | 특징                      |
| --------------- | --------------------------- | ------------------------- |
| **Development** | 개발자 자유 테스트          | 불안정 OK, 최소 사양      |
| **Staging**     | 프로덕션 동일 구성으로 검증 | QA 테스트, 최종 확인      |
| **Production**  | 실제 사용자 서비스          | 최고 안정성, 변경 시 승인 |

### 환경별 설정 비교

| 항목          | dev             | staging             | prod           |
| ------------- | --------------- | ------------------- | -------------- |
| **인스턴스**  | t3.micro × 1    | t3.small × 2        | m5.large × 4+  |
| **DB**        | 로컬/소형 RDS   | RDS (Single-AZ)     | RDS (Multi-AZ) |
| **도메인**    | dev.example.com | staging.example.com | example.com    |
| **로그 레벨** | DEBUG           | INFO                | WARN           |
| **배포 승인** | 자동            | 자동                | 수동 승인      |

### 환경변수로 분리하는 패턴

```yaml
# GitHub Actions에서 환경별 분기
jobs:
  deploy:
    environment: production # GitHub Environment로 승인 게이트 설정
    steps:
      - name: Deploy
        env:
          DB_HOST: ${{ secrets.DB_HOST }} # 환경별 다른 값
          API_URL: ${{ secrets.API_URL }}
```

> [!TIP]
> Step 8 실습에서는 단일 환경(prod)만 사용합니다.  
> 실무에서는 최소 dev/prod 두 환경을 분리하는 것을 권장합니다.

## 7. GitHub Actions 기본 구조

Step 8-2와 8-3 실습에서 사용할 GitHub Actions 워크플로우의 기본 구조입니다.

### 워크플로우 파일 위치

```
my-project/
└── .github/
    └── workflows/
        └── deploy.yml    ← 이 파일이 워크플로우 정의
```

### 기본 구조

```yaml
name: Deploy # 워크플로우 이름

on: # 트리거 조건
  push:
    branches: [main] # main 브랜치에 push 시 실행

jobs: # 실행할 작업 목록
  build-and-deploy:
    runs-on: ubuntu-latest # 실행 환경 (GitHub 제공 VM)

    steps: # 순차적으로 실행할 단계
      - name: Checkout
        uses: actions/checkout@v4 # 코드 가져오기

      - name: Build
        run: ./gradlew build # 빌드 명령어

      - name: Deploy
        run: | # 배포 스크립트
          aws s3 cp app.jar s3://bucket/
```

### 핵심 개념

| 용어         | 설명                                                          |
| ------------ | ------------------------------------------------------------- |
| **Workflow** | `.github/workflows/*.yml`에 정의된 자동화 파이프라인          |
| **Event**    | 워크플로우를 실행하는 트리거 (push, PR, schedule 등)          |
| **Job**      | 하나의 Runner에서 실행되는 작업 단위                          |
| **Step**     | Job 내에서 순차적으로 실행되는 개별 명령                      |
| **Action**   | 재사용 가능한 Step 모듈 (`actions/checkout@v4` 등)            |
| **Secret**   | 암호화된 환경변수 (AWS 키, DB 비밀번호 등)                    |
| **Runner**   | 워크플로우를 실행하는 가상 머신 (GitHub Hosted / Self-hosted) |

### Step 8에서 사용하는 배포 흐름

```
┌─────────────────────────────────────────────────────┐
│  프론트엔드 배포                                    │
│  Push → npm build → S3 sync → CloudFront 무효화    │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│  백엔드 배포                                        │
│  Push → Gradle build → S3 업로드                    │
│       → SSM Run Command → EC2에서 다운로드 + 재시작 │
└─────────────────────────────────────────────────────┘
```

> [!NOTE]
> GitHub Actions Public 리포지토리는 무료, Private 리포지토리는 월 2,000분 무료입니다.  
> 실습 수준에서는 무료 범위 내에서 충분히 사용할 수 있습니다.

## 핵심 정리

| 개념           | 한 줄 요약                                     |
| -------------- | ---------------------------------------------- |
| CI             | 코드 통합 시 자동 빌드·테스트                  |
| CD             | 검증된 코드를 자동으로 배포                    |
| 파이프라인     | 빌드 → 테스트 → 배포 자동화 흐름               |
| Rolling        | 서버를 순차적으로 교체                         |
| Blue-Green     | 두 환경 전환으로 무중단 배포                   |
| Canary         | 소수에게 먼저 배포 후 점진 확대                |
| GitHub Flow    | main + feature 브랜치 (단순, 빈번한 배포)      |
| 모노레포       | 하나의 레포에 프론트/백엔드 통합               |
| 멀티레포       | 프론트/백엔드 각각 독립 레포                   |
| 환경 분리      | dev/staging/prod 독립 운영                     |
| GitHub Actions | GitHub 내장 CI/CD 도구, YAML로 워크플로우 정의 |
